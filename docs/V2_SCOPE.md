# DevSupport Agent V2 — 范围与产品定位

> 状态：设计基线
>
> 本文是 V2 产品范围的来源文件。V0 / V1 文档保留为历史实现与验证记录；V2 开发开始后，如它们与本文冲突，以本文及其关联的 V2 文档为准。

## 1. 产品定位

DevSupport Agent V2 是供**可信小型研发团队内部使用**的、只读的微服务故障调查 Agent。

它接收用户描述的故障现象，从预先接入的运行数据与团队知识中收集证据，进行多轮假设验证，并交付可追溯的调查结论、未确认事项和人工建议。

它不是可观测性平台、通用运维平台或自主修复系统。DevSupport 消费团队已有的可观测性数据；它不负责搭建、运营或替代日志、指标、链路和发布平台。

## 2. 目标用户与部署假设

* 用户是同一团队内彼此信任的成员；所有可访问该实例的人默认共享调查记录与知识库。
* V2 部署在本机、可信内网或 VPN 后的环境；未经认证的实例不得直接暴露到公网。
* V2 不实现账号、登录、SSO、团队隔离、RBAC 或多租户。访问边界由部署网络负责。
* 调查目标、数据源地址和只读凭据由部署人员预先配置。普通用户不能提交任意 URL、Token、Shell、SQL 或代码。

## 3. V2 核心闭环

```text
用户创建 Incident
→ 选择已配置的调查目标和受影响服务
→ Agent 检索受范围约束的知识与运行证据
→ 形成、验证、更新 Hypothesis
→ 输出有引用的结论、置信度、未确认事项和人工建议
→ 生成该轮调查报告并终止
```

用户可在终态后补充新的观察信息，启动同一 Incident 的下一轮只读调查：

```text
补充现象
→ 保留历史结论与 Evidence
→ 新一轮收集新证据
→ 更新或推翻旧结论
→ 产生新版本报告
```

这不是恢复验证。V2 不记录或执行人工修复操作，也不声称系统已经恢复。

## 4. V2 必须证明

1. Agent 能在固定预算内完成可解释的多轮故障调查，而不是只回答单条日志问题。
2. 每项关键结论都绑定运行 Evidence 或知识 Citation；证据不足时必须明确为不确定。
3. Agent 只能通过白名单、结构化、只读 Tool 获取运行信息。
4. 相同 Tool Contract 可以通过不同 Adapter 查询不同的受支持可观测性平台。
5. 知识库按调查目标、服务和环境强制隔离，不能在检索中泄漏到不相关系统。
6. 不熟悉底层 Workflow 的团队成员也能用中文界面理解调查过程、证据、结论和下一步建议。
7. 一套新配置的微服务环境可在不改写 Agent Workflow 的前提下接入已有 Adapter；新的数据平台才需要新增 Adapter。

## 5. 业务对象

| 对象 | 职责 |
| --- | --- |
| 调查目标（Investigation Target） | 一套已配置的微服务环境，绑定可用数据源、服务范围与知识范围。 |
| 服务（Service） | 调查目标内可被选择和查询的服务标识。 |
| Incident | 用户报告的故障现象、时间范围、调查目标和受影响服务。 |
| 调查轮次（Investigation Round） | 一个 Incident 中一次独立、可追溯的调查执行。 |
| 用户观察（Observation） | 用户补充的现象或上下文；它是待验证输入，不自动成为事实。 |
| 假设（Hypothesis） | 可被 Evidence 支持、反驳或替换的故障解释。 |
| 证据（Evidence） | 有来源、时间和引用的运行数据或知识检索结果。 |
| 知识文档（Knowledge Document） | 归属于调查目标及范围的架构文档、Runbook、历史事故等。 |
| 报告（Report） | 一个调查轮次的不可变结论快照。 |

## 6. 调查状态

V2 使用以下用户可理解的 Incident 状态：

* `OPEN`：已创建，尚未开始调查；
* `INVESTIGATING`：正在进行某一轮调查；
* `CONCLUDED`：已形成有 Evidence 支持的调查结论；
* `INCONCLUSIVE`：调查正常结束但证据不足或存在无法消解的矛盾；
* `FAILED`：调查因受控系统错误而无法完成。

`CONCLUDED` 不等于业务系统已恢复。用户补充信息后，Incident 可从任一终态进入新的 `INVESTIGATING` 轮次。

## 7. V2 范围

### 7.1 只读调查

* Incident 创建、查看、调查进度和历史轮次；
* 假设与 Evidence 驱动的多轮调查；
* 日志、指标、可选 Trace、可选部署事实和知识检索；
* 结论、置信度、关键证据、未确认事项、人工建议与版本化报告；
* 用户补充观察后继续调查。

### 7.2 受控数据接入

* 固定的、结构化的 Tool Contract，例如 `query_logs`、`query_metrics`、`query_traces`、`search_knowledge`；
* 支持有限且明确的 Adapter；
* 调查目标在部署期配置数据源、Secret、服务映射和可用能力；
* Fault Lab 用于确定性开发与 Eval；OpenTelemetry Demo 用于真实数据源 Adapter 验证；
* V2 初期至少支持日志与指标；Trace 是可选增强，不阻塞首个内部试用。

### 7.3 知识库管理

* 中文知识库管理界面；
* 初期仅支持 Markdown 文件上传；
* 上传时选择调查目标、共享/服务范围、适用环境和文档类型；
* 文档解析、切分、Embedding、索引、状态与版本可见；
* 仅已启用且范围匹配的文档可被检索和引用。

### 7.4 中文调查体验

* 中文产品文案、V2 文档与调查报告；
* 调查概览、用户友好的时间线、关键证据、结论和建议为主视图；
* Tool 参数、内部节点和调试信息为默认折叠的技术详情。

### 7.5 内部部署基础

* 支持以 Docker Compose 在可信内网环境部署；
* 通过环境变量或等价 Secret 注入管理密钥；
* 提供健康检查、最小运行日志和数据库备份说明。

## 8. 明确非目标

V2 不包括：

* Agent 执行回滚、重启、发布、配置修改或任何副作用 Action；
* Approval、Action Execution、Recovery Verification；
* 公网匿名访问、SaaS、多租户、SSO、账号体系、RBAC；
* 用户自助填写任意数据源 URL、Token 或服务端点；
* 自建或运营 Prometheus、OpenSearch、Loki、Jaeger 等可观测性平台；
* 一次性支持所有日志、指标、链路厂商；
* Kubernetes、数据库、代码修改 Agent；
* Word、PDF、扫描件、OCR 等复杂知识导入；
* 把未经审核的 Agent 结论自动写入长期知识库。

## 9. 迁移原则

V2 允许对 V1 进行较大重写。应优先复用已经被验证有效的能力，而非为兼容旧流程保留不符合新定位的设计。

可评估复用的基础包括：PostgreSQL 持久化、LangGraph 状态编排、Pydantic Tool Schema、Hybrid RAG、Adapter Contract、Fault Lab、OpenTelemetry Demo、Eval 基础和已有 Web 工程骨架。

V2 运行路径不得暴露 V1 的回滚、审批或恢复验证 API、UI 和 Tool。
